Why This Document Exists

For months the ecosystem was built fast. Pages were created, components were shared, and a single JavaScript file gradually absorbed too many responsibilities. The result was a system that worked but could not be trusted. A fix in one place caused a regression somewhere else. The nav component was injecting footers, logos, CSS, persona logic, and ecosystem messaging all at once. Any change to it could touch everything.

This document captures the decisions made to stabilize that system, the governance model that now governs what can appear where, and the architectural changes that prevent the same failure modes from recurring.

This is not a session summary. It is an operating manual.

You were operating a system
without system rules.
Now you have them.

The Root Problem

The instability traced back to a single file: nav-component.js. Over time it had evolved from a navigation helper into a monolithic runtime override system. It was doing all of the following simultaneously:

What nav-component.js was doing

Injecting the header. Injecting the footer. Injecting a full CSS system. Managing theme state. Managing persona switching. Injecting the mobile drawer. Modifying logo assets. Injecting audience badges. Referencing StrategyIQ and The Hub by name in injected content. Applying Insights-specific modal logic. Running on every page across every channel.

This meant every Portal page, Hub page, and Insights article was inheriting decisions made inside one file. When that file was edited, mutations appeared everywhere. Double footers. Wrong logos. Leaked architecture. Styling regressions. None of them were random. They were all symptoms of the same root cause.

The fix

nav-component.js was replaced with a clean v14.2 that does exactly three things: renders the header, renders the mobile drawer, and manages theme state. It injects no footer. It makes no content decisions. It references no product names. It is infrastructure, not a brain.

Channel Governance Model

The four ecosystem channels now have explicit rules about what they can and cannot say, reference, or expose. These rules exist to prevent accidental leaks of architecture, product naming, and system relationships into contexts where they do not belong.

Channel 01
The Hub

The ecosystem explainer. The only channel allowed to name and describe all components publicly, including StrategyIQ, Advisory, Studio, and Portal. This is where the full architecture is explained. Users arrive here to understand how everything fits together.

Channel 02
The Portal

Product-first, singular. StrategyIQ is never named publicly here. The Hub is not foregrounded. The Portal presents itself as a complete operating environment. Users arrive here to engage with the product, not to understand the system.

Channel 03
Insights

Selective and editorial. StrategyIQ and Hub references are allowed only in articles specifically about building the ecosystem. General articles, reflections, and use cases avoid system architecture language entirely.

Channel 04
Portfolio

Contextual and restrained. StrategyIQ does not appear here at all until it is publicly trademarked and launched. The Portfolio is about Luis the professional. The Hub and Portal can be linked but the Portfolio does not read like a product brochure.

Navigation governance rule

Navigation makes the Portal discoverable. Content makes it desirable. Only send users to the Portal when they are ready to arrive.

Architectural Decisions

Decision 1 — nav-component.js is infrastructure only

The nav component is responsible for exactly three things: rendering the header, rendering the mobile drawer, and managing theme state. It is never the place where ecosystem messaging decisions are made. If a decision changes based on which channel you are on, that decision lives in the page HTML, not in the nav component.

Decision 2 — Portal gets its own dedicated nav

Portal pages no longer use nav-component.js. A dedicated portal-nav.js was created from scratch. This means changes to nav-component.js can never accidentally affect Portal pages. Changes to portal-nav.js can never affect Hub pages. Each file has a single, clear responsibility.

Why this matters

The previous architecture used nav-component.js path detection to conditionally change behavior per channel. Every new condition added fragility. The dedicated nav removes that fragility entirely. Portal equals Portal. Hub equals Hub. Nothing leaks accidentally.

Decision 3 — StrategyIQ is a hidden engine until trademark

StrategyIQ is the diagnostic intelligence at the core of the system. It is not publicly named on Portal pages, Portfolio pages, or in general Insights articles. It is named only on Hub pages, where the full architecture is intentionally explained. This decision is in place until a trademark is secured and a public launch is planned.

Failure Modes

These are the specific breakdowns that occur when governance rules are violated. Each one has been observed or narrowly avoided during the stabilization session that produced this document.

StrategyIQ appears on Portal pages

Product clarity collapses. The Portal is supposed to feel like a complete, self-contained operating environment. Naming the engine that runs it breaks the product illusion and forces users to understand architecture before they can understand value.

nav-component.js makes content decisions

The system becomes unstable. This is the root cause of the double footers, logo regressions, and mutation cascades that triggered this stabilization session. The moment the nav file starts deciding what to show based on channel context, every edit to it becomes a potential regression across every channel simultaneously.

Advisory page references upstream or downstream dependencies

The capability reads as a step in a process rather than a standalone service. Dependency language shifts the frame from outcomes to architecture — and architecture is not what a client is buying.

Portfolio references the ecosystem architecture

Credibility dilutes. The Portfolio is proof of professional capability. The moment it starts explaining The Hub, The Portal, or StrategyIQ, it stops being evidence and starts being a sales document. These are different audiences with different questions. Mixing them weakens both.

Portal and Hub share a nav component with conditional logic

Fragility accumulates silently. Every new channel-specific condition added to a shared nav file is a hidden coupling between channels that should be independent. The failure mode does not announce itself until a change intended for one channel breaks another.

Insights articles name StrategyIQ outside the Building Series

The editorial voice becomes promotional. Insights authority comes from the quality of thinking, not from promoting products. Introducing product architecture into editorial articles shifts the reader's trust relationship with the content.

Governance Rules — Quick Reference

nav-component.js scope

Header rendering. Mobile drawer. Theme state. Nothing else. If a decision changes based on channel, it lives in the page HTML, not in this file.

portal-nav.js scope

Portal header rendering. Portal mobile drawer. Theme state. No ecosystem messaging. No StrategyIQ. No Hub sub-pages. No megamenu.

StrategyIQ naming rule

Named only on Hub pages. Not on Portal pages, Portfolio pages, or in general Insights articles. This rule holds until trademark is secured and public launch is planned.

Portal CTA language rule

Every Portal CTA should imply that something intentional and structured is on the other side. The user should feel like they are being admitted into something, not clicking a link. Avoid: "Learn more", "Explore the Portal", "Visit the Portal." Prefer: "Enter the system", "See how this operates", "This is where strategy runs."

Advisory standalone rule

Advisory must read as a complete, standalone capability. No dependency language. No references to StrategyIQ as an upstream input. No references to The Portal or The Studio as downstream steps. Replace process language with outcome language: decisions, clarity, direction, outcomes.
